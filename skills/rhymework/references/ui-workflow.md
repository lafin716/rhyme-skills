# 기존 이미지·UI 워크플로

실제 이미지/UI 작업에서만 로드한다. 기존 Rhymework의 구현·통합·검증 절차를 보존한다. 프로젝트 모드에서는 각 검증 결과를 해당 Task의 증거로 연결한다.

여러 화면의 디자인은 기존 DESIGN.md를 따른다. 색상·타이포·여백·이미지 스타일·텍스트 안전 영역·터치 크기·오류/빈 상태를 먼저 합의한다. 문서가 없으면 작업 크기에 맞는 최소 메모만 만든다.

## 4. 이미지와 UI 구현

- 기존 래스터 이미지를 변경할 때는 먼저 확인하고, 제공되는 이미지 생성/편집 스킬과 도구를 사용한다. SVG·CSS 등 코드 기반 비주얼은 기존 방식으로 수정한다.
- 각 이미지의 구도·재질·빛·색상·밀도를 공통 기준에 맞춘다. UI가 덮는 영역과 실제 보이는 영역을 고려하고, 조작·문구는 코드로 렌더링한다.
- 생성 결과를 직접 확인한 뒤 실제 프로젝트 자산에 적용한다. 단순 재색칠이나 임시 도형을 완성된 새 이미지라고 보고하지 않는다. 도구 실패 시 허용되는 대안을 쓰되 품질과 출처를 정직하게 기록한다.
- 필요한 경우 실제 사용한 프롬프트, 원본, 설치 경로, 크기를 기존 자산 기록에 남긴다. 자산 교체로 오래된 검토 점수나 설명이 사실과 달라지면 갱신한다.
- 정상·빈 상태·부족·최대치·성공·취소에서 다음 행동이 읽혀야 한다. 비활성 버튼의 글자 대비와 이유, 페이지 이동, 닫기, 복귀 경로를 확인한다.

## 5. 리더 통합과 독립 리뷰

에이전트의 완료 보고를 모아 실제 diff와 결과물을 확인한다. 공통 스타일·크기·여백·문구·인터랙션을 통합한다. 버튼/오브젝트의 보이지 않는 히트 영역도 검사한다.

구현자와 별도의 리뷰 에이전트에게 변경 범위와 계획을 제공한다. 실제로 발생 가능한 오류, 모달 중첩, 타이머/리스너 정리, 중복 결제·날짜 진행, 공유 컴포넌트 회귀를 검토하게 한다. 발견한 문제는 수정하고 관련 검증을 다시 실행한다.

## 6. 실제 검증과 수정 반복

코드 검토만으로 시각 작업을 완료하지 않는다. 최종 코드를 실행하고 대표적인 좁은 화면과 다른 지원 크기에서 스크린샷을 직접 확인한다. 배경에 묻힌 글자, 카드 밖 텍스트, 잘림, 버튼/터치 겹침을 발견하면 고치고 다시 확인한다.

주요 행동은 실제 UI로 실행하고 전후 상태를 비교한다. 구매·먹이·판매 등은 금액/재고/경험치, 취소는 상태 유지, 날짜 진행은 한 번만 발생하는지 확인한다. 관련 없는 시나리오를 의무적으로 추가하지 않는다.

검증용 fixture가 필요하면 실제 앱 컴포넌트를 사용하고 전용 테스트 데이터/저장 공간으로 격리한다. 캔버스 위 QA 도구는 앱 입력으로 클릭이 새지 않게 하며 초기화 완료 후 조작한다. 화면 크기나 코드 변경 후 새 상태가 반영됐는지 확인한다. 브라우저 도구의 제약을 우회하지 않는다.

변경에 맞는 테스트·타입 검사·린트·빌드를 실행한다. 테스트는 의미 있는 동작 위험을 검증할 때 추가한다. 검증 불가 항목은 대체 근거와 남은 한계를 기록한다. 새로운 수정·실패가 없다면 같은 검사를 불필요하게 반복하지 않는다.
