# task-queue — 작업을 큐에 적어 두기

인자: `$ARGUMENTS` (비어 있으면 이번 대화에서 사용자가 말한 할 일을 쓴다. 그것도 없으면 무엇을 넣을지 한 번만 묻는다)

이 스킬은 **적어 두기만 한다.** 소스 코드·설정·의존성을 바꾸지 않고, 커밋·푸시·외부 전송도 하지 않는다. 구현은 `task-run`이 한다.

## 파일 위치

프로젝트 루트(git 저장소면 최상위)에 둔다.

| 경로 | 내용 |
|---|---|
| `QUEUE.md` | 작업 목록. 사람이 직접 고쳐도 된다 |
| `.queue/<ID>/` | 작업별 사전 준비 자료 (필요할 때만) |

- 프로젝트에 이미 큐 파일 관례(예: `docs/QUEUE.md`)가 있거나 지침 문서가 위치를 정했으면 그것을 따른다.
- `.gitignore`는 건드리지 않는다. 큐를 커밋할지는 사용자가 정한다.

## QUEUE.md 형식

파일이 없으면 아래 머리말로 만든다.

```markdown
# 작업 큐

task-queue 스킬이 적고 task-run 스킬이 처리한다. 끝난 항목은 지워진다.
항목 순서가 처리 순서다(우선순위 높음이 먼저). 직접 고쳐도 된다.

## Q-1 · 버그 · 지식베이스 팝업을 열면 스크롤이 맨 위로 튄다
- 추가: 2026-11-13
- 우선순위: 높음
- 요청: (사용자가 한 말을 그대로, 길면 핵심만)
- 완료 기준:
  - 팝업을 다시 열어도 이전 스크롤 위치가 유지된다
- 메모: 관련 화면·재현 방법·제약 등 (없으면 생략)
- 의존: 없음 (먼저 끝나야 하는 항목 ID)
- 준비: .queue/Q-1/ — 원인 후보 2개, 관련 파일 3개 (준비하지 않았으면 "없음")
```

- **ID**: `Q-<번호>`. 번호는 `QUEUE.md`의 항목과 `.queue/` 폴더 이름 중 가장 큰 번호 + 1. 큐가 비어 있으면 1부터 다시 시작한다.
- **종류**: `기능` · `버그` · `개선` · `리팩터` · `문서` · `조사` 중 하나.
- **우선순위**: `높음` · `보통` · `낮음`. 사용자가 말하지 않으면 `보통`. 버그로 데이터가 손실되거나 앱이 실행되지 않으면 `높음`.
- 새 항목은 같은 우선순위 묶음의 맨 끝에 넣는다(높음 → 보통 → 낮음 순서 유지).
- **완료 기준**은 확인할 수 있는 문장으로 쓴다. 요청이 모호하면 합리적으로 해석해 적고 메모에 `가정:`으로 남긴다. 구현 방법이 갈리는 중요한 결정만 `확인 필요:`로 남긴다(질문하지 않는다. task-run이 처리 전에 묻는다).

## 절차

1. **요청 나누기**: 한 메시지에 할 일이 여러 개면 서로 독립적으로 끝낼 수 있는 단위로 항목을 나눈다. 너무 잘게 쪼개지 않는다(같은 화면의 문구 세 개 수정은 한 항목).
2. **중복 확인**: `QUEUE.md`의 기존 항목과 같거나 겹치면 새로 만들지 않고 기존 항목의 요청·완료 기준·메모에 내용을 보탠다. 이미 구현돼 있는지도 코드에서 가볍게 확인하고, 그렇다면 넣지 않고 그 사실을 보고한다.
3. **맥락 기록**: 사용자가 대화에서 보여 준 오류 메시지·스크린샷 설명·재현 방법은 나중에 사라지므로 메모나 준비 자료에 옮겨 둔다.
4. **사전 준비 판단** (아래 기준).
5. **QUEUE.md 쓰기**: 형식을 지키고 다른 항목은 건드리지 않는다.
6. **보고**: 추가·갱신한 항목 ID와 제목, 준비 자료를 만든 항목과 요약, 현재 큐 개수. 처리하려면 `/task-run`을 쓰면 된다고 한 줄 덧붙인다.

## 사전 준비 (.queue/<ID>/)

나중에 구현할 때 시간을 확실히 줄여 주는 경우에만 만든다. 모든 항목에 만들지 않는다.

**준비하는 경우**
- 원인을 모르는 버그: 관련 코드 위치, 재현 경로, 원인 후보를 미리 좁혀 둘 수 있을 때
- 외부 라이브러리·API·플랫폼 동작을 알아봐야 하는 작업: 공식 문서 요점, 버전별 차이, 예제
- 여러 파일·모듈에 걸친 변경: 영향 범위와 수정할 파일 목록
- 설계 선택지가 있는 작업: 선택지 2~3개와 추천, 그 이유
- 사용자가 준 자료(오류 로그, 사양, 링크 내용)를 보존해야 할 때

**준비하지 않는 경우**
- 파일 한두 개를 고치면 끝나는 작은 작업, 위치가 이미 분명한 작업
- 조사 결과가 금방 낡을 내용(곧 바뀔 브랜치의 세부 줄 번호 등)

**파일 구성** (필요한 것만)

| 파일 | 내용 |
|---|---|
| `NOTES.md` | 필수. 요약, 관련 파일(`경로:줄`), 원인 후보 또는 구현 방향, 추천 접근, 남은 의문, 조사 시점의 `git rev-parse --short HEAD` |
| `refs.md` | 외부 문서 요점과 출처 URL |
| `repro.md` | 재현 절차, 오류 메시지 원문 |
| 그 밖 | 사용자가 준 로그·사양 사본, 작은 실험 스크립트 |

**규칙**
- 읽기 전용 조사만 한다. 저장소 파일을 고치거나, 의존성을 설치하거나, 데이터·외부 서비스에 쓰지 않는다. 실험 스크립트는 `.queue/<ID>/` 안에만 두고 실행하지 않아도 된다.
- 비밀 값(API 키, 토큰, 개인 정보)은 자료에 옮기지 않는다. 로그에 있으면 가린다.
- 조사는 짧게 한다. 원인을 끝까지 찾는 것은 task-run의 몫이다. 확실하지 않은 내용은 "추정"이라고 적는다.
- 준비를 마치면 QUEUE.md 항목의 `준비:` 줄에 폴더 경로와 한 줄 요약을 적는다.
